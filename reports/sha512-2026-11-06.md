# SHA-512 measurements, 2026-11-06 (superseded: the project uses SHA-256, see docs/DESIGN_DECISIONS.md D12)

Host: Ryzen 7 5800X (sha_ni, avx2, bmi2; no SHA-512 instructions), RTX 3090 Ti (PCIe Gen4 x8, idle apart from the compositor), CUDA 13.4, GCC 16.2.1, OpenSSL 3.6.5. One run per configuration.

## CPU

| Path | Command | Result |
|---|---|---|
| xksm scalar C | `build/bench_sha512 256 5` | GB/s min 0.574, median 0.577, max 0.578 |
| OpenSSL reference | `openssl speed -seconds 2 -bytes 16384 sha512` | 1.094 GB/s (1093512.62k) |

Correctness: FIPS 180-2 vectors (4) and chunked streaming in `tests/test_sha512.c`; 18 random files of 0 to 1048577 bytes identical to `openssl dgst -sha512`.

## GPU batch (one thread per message)

Command: `bench_sha512_cuda 65536 8192 5`, built with `nvcc -O3 -arch=sm_86 -std=c++17`. The SHA-512 sources were taken out of the tree after this measurement; they are in commit a9f46d6.

```
NVIDIA GeForce RTX 3090 Ti, 65536 messages, lengths 0..8191, 255.9 MiB of message bytes, 5 repeats
digest mismatches GPU vs CPU: 0 / 65536
cpu 1 thread    :   474.74 ms    0.565 GB/s
gpu kernel      : min    4.168  median    4.553  max    4.882 ms  -> median   58.93 GB/s
h2d (pinned)    : min   20.010  median   20.029  max   22.168 ms  -> median   13.41 GB/s
d2h digests     : median    0.322 ms
end to end      : median   24.905 ms  ->   10.77 GB/s, 19.06x the 1-thread CPU
```

Reading: the kernel (58.93 GB/s) is 4.4x faster than the host-to-device copy, which takes 80 % of the end-to-end time. Overlapping copy and kernel with streams is the next step; its bound is the copy alone (about 13 GB/s, arithmetic, not measured). Kernel inefficiency (warp divergence from mixed lengths, per-lane uncoalesced loads) is suspected and not yet measured. A multi-threaded CPU comparison has not been run.

## Store size: 64-byte vs 32-byte digests

50,000 memories in the schema v1 store, byte-identical placeholder text in both stores
(random hex split into tokens), WAL checkpointed, file size from `stat`, table size from
`dbstat`. Raw output: `benchmarks/out/sizes.txt` (local, not committed).

| Chunk | 64-byte digest file | 32-byte digest file | Saved |
|---|---|---|---|
| 256 B | 38,346,752 B | 36,483,072 B | 1,863,680 B, 4.86 % |
| 1024 B | 131,010,560 B | 131,010,560 B | 0 B |
| 4096 B | 467,288,064 B | 467,288,064 B | 0 B |

At 1024 and 4096 bytes the rows pack into the same number of 4,096-byte pages either way,
so the 32 bytes per row are absorbed by page slack. Where hashing runs (CPU or GPU) does not
affect storage.

FTS5 `detail` option at 1024-byte chunks: full 59,457,536 B, column 59,424,768 B, none
53,190,656 B of index; `column` and `none` reject phrase queries
("phrase queries are not supported (detail!=full)"). Random-hex tokens make the term
dictionary unusually large, so these index sizes are pessimistic for natural text.
